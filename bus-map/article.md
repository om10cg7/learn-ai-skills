広島のバスが「いまどこを走っていて、どれだけ遅れているか」を、一画面で眺められる地図サイトを作りました。「広島バスマップ」という名前で、データは広島県バス協会が公開している GTFS-RT（15秒更新）です。

👉 実際のサイトはこちらです。スマホでもパソコンでも開けます。
https://bus.ana8labo.com/

設計から公開の手前まで、約5日間。Claude Code に7つの役割（サブエージェント）を持たせて進めました。この記事では、何を作ったか、どう分担したか、そして15秒ルールを守るコードが逆に30秒間隔を生んだ話など、つまずいた点をまとめます。

## 🛠 環境

- OS：Windows 11 Pro
- Python 3.11.9 / FastAPI 0.142.2 / Docker 29.6.1
- DB：MariaDB（既存の共用コンテナの中に専用データベースを作成）
- 画面：HTML と素の JavaScript、地図は Google Maps JavaScript API
- Claude Code でサブエージェント7体を使用

## 🤔 作ろうと思った理由と、作ったもの

広島には、バス協会が運用する「くるけん」という公式のバスロケがあります。バス停を起点に、次のバスがあと何分で来るかを見るのには、とても便利です。

ただ、私が見たかったのは別のものでした。街全体のバスが、いま全体として遅れているのか、定刻どおりなのか。それを地図の上で一目で見たかったのです。

くるけんと競うつもりはなく、役割を分けます。このサイトは街の状態を眺める道具にして、正式な接近案内は、画面からくるけんへ案内します。収益化もしません。

開くと、その時点で走っているバスが地図に出ます。位置情報の利用を許可すると、現在地を中心に表示されます。拒否した場合は、紙屋町が中心です。

できることは、次のとおりです。運行中のバスを地図に表示し、遅れを5つの区分で色分けします。対象は、広電バス、広島バス、広島交通の3社です。

- 運行中の台数と、遅れている台数を上部に表示
- 停留所を選ぶと、30分以内に来るバスだけを残し、「次に来る3件」を表示
- バスをタップすると、系統・行き先・遅れ・次の停留所を表示
- 地図が出せないときは、遅れている系統の一覧に切り替え
- 取得状況を見る専用ページ

位置は保存しません。DB に入れるのは、事業者のマスタ、静的な時刻表データ、運用の記録だけです。

## 📡 まず、実データを録音して確かめた

動く試作を作る段階で、配信元のデータを3回だけ録音して中身を確認しました。開発とテストで配信元を叩かないよう、録音したものをテスト用に使うためでもあります。

3社とも、車両の位置と便ごとの遅れは1対1で対応していました。録音時の車両数は、広電224台、広島バス72台、広島交通77台です。便の ID は、静的な時刻表データと100%一致しました。

一方で、想像と違う点がいくつもありました。

- 便全体の遅れの値は入っておらず、遅れは「停留所ごと」に入っている
- 遅れの値は60秒単位
- 車両の位置データには、次の停留所の番号が入っていない
- 行き先は `trip_headsign` ではなく、`stop_times.txt` の `stop_headsign` にある（前者は「市役所経由」のような経由地）

こうした違いは、実際に録音してみるまで分かりませんでした。

## 🏗 設計：配信元に負荷をかけない

配信元からは、「高頻度のアクセスはご遠慮願います」と案内されています。そこで、取得は専用のプロセス（worker）が1つだけ行い、画面を返すプロセス（web）は、その結果を読むだけにしました。

閲覧者が増えても、配信元へのアクセスは増えません。取得の間隔は、車両の位置と遅れが15秒、運行情報が60秒です。この下限はコードに固定してあります。

worker が複数立ち上がって二重に取得しないよう、DB のロックで1つに絞っています。web には、DB の更新権限を持つ認証情報を渡しません。

Google マップには、1日の表示回数の上限（300回）を決めました。上限に近づくと、画面は自動で地図から一覧表示に切り替わります。アクセスが集まった日は、地図ではなく一覧が出ることがあります。

## 🤖 7つの役割と「未決事項ノート」

Claude Code には、役割ごとのサブエージェントを用意しました。設計が3体、実装が4体です。

- 設計：サーバー側の設計、画面の設計、設計レビュー
- 実装：バックエンド、フロントエンド、テスト、コードレビュー

進め方の順番も決めてあります。テストの骨組み、バックエンド、フロントエンド、コードレビュー、修正1往復の順です。

特に効いたのが、`CLAUDE.md` に書いた次のルールです。仕様にない判断は自分で決めず、`open-questions.md` に質問として積み、私が答えます。

質問は Q-059 まで番号が付きました。「停留所をどれだけ近ければ同じ停留所とみなすか」のような小さな判断も、AI が黙って決めず、記録が残ります。後から「なぜこうなっているか」を追えるのが助かりました。

## ⚠️ つまずいたところ

### 15秒ルールを守るコードが、30秒間隔を生んだ

取得の下限は15秒と決めていて、コードにも固定しました。ところが、コードレビューで、ループの開始が数ミリ秒早いと、その回の取得を飛ばして30秒間隔になることが見つかりました。15秒に届いていないと判定されるためです。

直したところ、今度は別の問題が出ました。下限の判定が「予定時刻」を基準にしていたため、実際の取得時刻とずれます。ロック待ちや DB への記録に時間がかかると、連続する2回の実際の間隔が、15秒を切る可能性があったのです。

直し方は、判定と記録を「取得リクエストを出す直前の実時刻」に変えることでした。この種の下限は、予定ではなく実際の時刻で守る必要があります。

### 取得が止まっても、到着見込みが減り続けた

QA の段階では、取得が止まっても「あと◯分」が減り続ける不具合が見つかりました。配信元が止まっているのに、画面上ではバスがどんどん近づいてきます。

また、時刻表では走っているはずなのに0台のときも、「始発は0時台」と出ることがありました。昼間にそう出たら、利用者は混乱します。QA で見つけた20件は、すべて修正済みです。

### 「同じ docker ネットワークの全員を信頼する」構成になっていた

公開側のサーバーは、連打を防ぐために、Cloudflare が付ける接続元の情報を見ています。レビューでは、ポートを `0.0.0.0` に開けると、外から偽装できることが指摘されました。

docker のポート公開では、外部の接続が、内部のゲートウェイ経由に見えるためです。ポートは `127.0.0.1` にバインドしたままにし、理由をコメントに残しました。

最後に、レビューの件数です。公開前のレビューは2回行いました。合わせて約40件の指摘が出ました。1回目は18件（高1・中7・低10）、2回目は20件（高2・中7・低11）です。指摘の番号は、その後の機能追加を含めて C-045 まで進みました。

自分で書いたつもりのコードでも、別の役割の目で見ると、これだけ出ます。

## ✅ くるけんと突き合わせてみた

遅れの値が正しいか、くるけんの表示と比べました。3社8台について、くるけんの「時刻表の時刻」と「あと◯分」から遅れを逆算し、このサイトの値と比べます。結果は、1分以内で一致しました。

ただし、くるけん側の値は表示からの逆算で、「約5〜6分」のような幅があります。正確な突き合わせとは言えません。遅れの値が60秒単位なので、「ほぼ定刻」と「遅れ」の境（3分）付近では、1分の差で区分が変わります。

2026年10月8日の朝7時51分の時点では、運行中544台のうち285台が「遅れ」でした。約5割です。録音した10月7日の夕方にも、同じくらいの割合でした。2回の観測だけなので、いつもそうだとは言えません。
